# Pi MCP 设计依据与综合决策

## 问题与目标

让 Pi 使用管理员配置的外部 MCP tools，沿用 cs-agent 的回合身份、会话隔离和 Pi durable 生命周期，不支持 OAuth。本文保留设计阶段的候选比较；首版现已实现，启用方式与验证记录见 [使用说明](../../PI-MCP.md) 和 [完整设计](../../PI-MCP-DESIGN.md)。

现有 Registry 支持工具 schema 和会话选择，ToolTask 已有执行意图、结果提交以及 safe/unsafe 恢复。新设计应补上外部协议边界，而非复制这些能力。

## 调用方与结构

PiBackend 在 Harness 暂停调度时 attach PiMcp，在每轮 configureTools 内配置可见工具，在既有 Harness 关闭后释放 MCP。模型直接使用每个远端工具的参数 schema。元数据读取供现有 trace hooks 使用，SDK Client、秘密和连接不能逃逸出模块。

一个不可变目录是定义的唯一事实源，Registry 与会话选择可以从它恢复。会话连接按真实主体、凭据引用版本和 conversationId 隔离。目录更新先持久提交、再安装和选择，不依赖跨库事务。

## 两个独立候选的比较

| 维度 | 权重 | A：原生逐工具 | B：固定 Gateway |
| --- | ---: | ---: | ---: |
| 现有层次与生命周期 | 25 | 24 | 19 |
| 身份与隔离 | 20 | 18 | 16 |
| 恢复、版本和取消 | 20 | 18 | 18 |
| 接口深度与维护负担 | 15 | 14 | 11 |
| 配置与无 OAuth 范围 | 10 | 6 | 7 |
| 测试与可观测 | 10 | 9 | 8 |
| 总计 | 100 | 89 | 79 |

这是按事先给定权重进行的设计评审分数，表示评审判断，不是性能或可靠性实测。候选完成后进行了只读交叉评审；最终文档仍由主设计综合，分数不代替具体理由。

选 A 为基底。原生方案把真实 schema 交给模型，使用现成 ToolTask；首版全 unsafe，不增加调用日志。B 以 discover/describe/call 隐藏目录变化，但增加模型使用步骤；要对远端工具分别恢复，固定 call 必须成为 safe 本地外壳并增加持久状态判定及管理解除流程。

从 B 吸收有界队列、含排队/连接的总调用预算、完整错误矩阵和明确的 unknown 语义。未知操作账本、强制重复阻断与选择性 safe 留给明确需要它们的后续需求，不同时保留两条工具调用入口。

## 评审后修订

1. owner 权限精确限定在 owner 私聊主会话；owner 群聊仍拒绝。
2. 秘密来自显式环境引用，配置/凭据版本通过管理员更新后重启生效；不引入自动轮换平台，不暗示热重载已实现。
3. 调用、目录、连接及恢复终态使用不同审计事件形状。unsafe 恢复绕过 afterTool，靠既有事件观察补齐；MCP 的通用输入/输出日志分支必须收紧。
4. 子 agent 的父工具复制过程显式过滤 MCP；不能仅靠 execute 拒绝来避免泄漏 schema。

## 接受的代价

- 版本化 Registry 和历史目录占用空间，因此设置容量上限并保守清理。
- unsafe 会中断一部分实际上未发送的操作，这是无法证明远端是否执行时的保守选择。
- 首版限制 owner 私聊、子 agent 不可调用，便于验证外部账号与现有群聊历史边界。
- 无跨业务 exactly-once；模型新建调用仍可能重复操作。需要服务端幂等或本地 unknown 阻断时显式设计，不以重连代替它们。
- MCP 无服务端工具版本锁定字段，客户端目录 hash 无法消除远端 list/call 竞态。

## 验证与后续

实现已用本机 HTTP fixture、真实 ThreadHost/PiBackend 与 pi.sqlite 验证权限、目录版本、关闭顺序、审计脱敏及 unsafe 崩溃后不自动重发。真实 SIGKILL 测试覆盖未收到响应和已提交成功结果两个窗口。

严格 schema 子集与解析前消息限额均有契约测试。模型工具定义预算包含名称、描述和输入 schema；目录达到容量上限后拒绝新版本。剩余部署工作是针对实际服务配置凭据和白名单，并确认长期目录规模；本次未连接生产服务。
