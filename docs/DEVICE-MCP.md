# 个人设备与持久 VM 的 Cua 接入

cs-agent 通过名为 `cua` 的反向 MCP 访问自托管的 Cua Spaces。设备卡给出名称、完整 Space ID、系统和上游报告的状态。模型先用 `list_spaces` 找到设备，再在后续调用中传回同一张卡的完整 ID。

| 工具 | 参数与结果 | 谁可以调用 |
| --- | --- | --- |
| `list_spaces` | 返回当前会话可见的设备卡 | 主人及获分配设备的会话 |
| `list_tools` | 传入 `space` 和 `service=driver`，可用 `name` 筛选 Driver 工具并查看参数 | 同上 |
| `get_hostname` | 传入 `space`，在设备上执行固定的 `hostname` 并返回实际主机名 | 主人当前的交互回合 |
| `get_window_screenshot` | 传入 `space`、目标进程 `pid` 和 `window_id`，获取 macOS 上该窗口的一张 PNG | 主人当前的交互回合 |

后两项需在控制机上为目标设备启用专用回环路由，并在管理台启用对应工具。定时任务、子任务、群聊和其他私聊只能按原有权限查看目录。截图需要调用者提供目标窗口的两个数值 ID。工具在抓取前后核验窗口归属，长边最多 768 像素；所属进程已变、窗口关闭或系统拒绝抓取时返回错误。Worker 将图片写入当前会话的私有媒体库。回复需要带图时，将结果中的 `structuredContent.imageId` 放入 `send_message.images`。Windows 真机的截图尚待单独验证。

## 控制端与设备

| 位置 | 职责 |
| --- | --- |
| Cloudflare Worker | 托管对话、操作权限、MCP 工具目录与结果。现有反向 WebSocket 接受经过认证的 MCP 节点，管理台可查看注册节点的连接状态。 |
| 自建 VPS | 运行 Static Mode Relay 和聚合 `cua daemon`。控制端保存每台设备的目录和独立凭据。聚合 MCP 仅供 VPS 本地访问，反向桥负责连接 Worker。 |
| Mac、Linux、Windows VM | 在设备侧运行 Cua 的设备服务和所需的 Driver。Windows 持久 VM 使用来宾内的交互用户。桌面可用性取决于用户登录状态和本机授予的权限。 |

静态模式需要核对设备身份。Cua SDK 0.31.0 按主机名和端口构造 `direct:<host:port>`。同一 Relay 的多个 URL 即便路径含有不同 machine ID，在聚合目录里仍可能得到同一个 ID，后登记的设备可能覆盖原端点。每台设备需要独立且稳定的内部主机名或端口，并将该地址和允许注册的设备身份绑定。换机时先撤回原分配，核对新设备身份后再授权。[Cua 0.31.0 的设备登记实现](https://github.com/trycua/cua/blob/cua-sdk-v0.31.0/libs/cua/crates/cua-spaces/src/spaces.rs#L1322-L1382)

公网入口只接受所需的设备注册流量。设备代理路径 `/m/<machine-id>/…` 和聚合 MCP 仅能从内部访问。设备与控制端凭据分开保存，按各自身份鉴权。管理台中的「节点在线」表示反向桥已连接 Worker。设备状态和 Driver 工具目录要从对应的 Space 查询。安装步骤、按设备分配端口的示例和凭据轮换方式见[控制机部署指南](../deploy/cua/README.md)。

## 会话分配与生产验收

主人在「权限与运维」中的「设备按会话分配（Cua）」为指定的 `group:<id>` 或 `private:<id>` 勾选设备。主人可查看整个目录，其他会话只能查询获准设备的卡片和 Driver 工具说明。子任务可查询的设备取派出时清单与当前分配的交集。给群聊或私聊分配设备只开放两项目录查询。普通第三方 MCP 和 WSB 的工具授权和审批单独配置。

上线前在至少两台可区分的测试机上逐项验收。

1. 在纯自托管配置下，确认控制端和设备都能运行。重启其中一台后核对两台的稳定 ID 和实际主机名，再核对旧身份无法接管新分配。
2. 在主人会话列出两台设备的名称、系统和完整 ID。分别查询 Driver 工具说明，对照设备自身的工具目录，核实响应确实来自选定设备。在启用了读取路由的测试 Mac 上，执行 `get_hostname` 并与本机返回值核对；打开专用测试窗口，给出其 PID 和窗口 ID，验证 `get_window_screenshot` 的图片能回到发起调用的对话。关闭窗口后重试，应返回错误。
3. 仅向一个测试会话分配设备 B。核对目录只显示 B，指定设备 A 的调用被拒。派发子任务后撤销 B，再核对其下一次调用被拒。核对群聊和子任务都看不到主人专用的两项读取工具，手动指定工具名也会被拒绝。
4. 中断桥接连接，验证设备目录不可查询、已有分配仍可撤回。恢复连接后重新读取目录，并核对普通 MCP、QQ 收发及 WSB。

上述步骤是生产切换前置条件。公网 443 上的自托管 Relay 已用临时设备验过注册、目录查询和重连。两台真实设备之间的隔离及生产 Worker 切换仍需在目标部署验收。

## 从旧设备服务切换

1. 升级前在旧管理台记录每台设备的名称、UUID、MCP 地址和 Tunnel/DNS 对应关系。结束旧任务、导出仍需的收据，检查定时任务及自定义技能中保存的旧工具名。用旧版管理台逐台撤销设备接入，确认旧路由返回 404。
2. 在设备上用原客户端和当时的登录账户运行 `node cs-agent-device.cjs remove-service`。使用自定义状态目录时提供原 `--state-dir`。停掉手工启动的进程。旧独立桌面及 Hyper-V 来宾可能另有 `CsAgentDesktopMcp`、`CsAgentHypervShellV1`、`CsAgentHypervDesktopV1` 计划任务，按实际安装情况停用。保留项目盘和需要的历史收据。
3. 对照升级前的清单，逐项删除只供旧设备使用的 Cloudflare Tunnel 和 DNS 记录、撤销其专用凭据。CS2 Workshop、WSB 或其他服务可能仍使用自己的 Tunnel。Cloudflare 账户管理使用独立授权。
4. 新版 Registry 初始化时清理旧配对表、工具别名，以及能与配对记录或旧桌面工具契约准确匹配的 MCP 记录。人工改名或改址的服务需由管理员核实。生产设备的自启动、外部脚本和 Cloudflare 资源都需单独清退。

升级会将服务 ID `cua` 保留给设备目录。如果旧版本已有同名 MCP，先记下其用途并使用其他 ID 重新配置。新版会清除旧 `cua` 的登记和凭据，管理员需要为目录桥重新登记并分配。

回退 Worker 只能恢复旧程序。恢复旧配对记录需要切换前的备份或重新登记。持久 VM 的磁盘由设备所有者管理，WSB 宿主机原有任务账本和环境 ID 保留。
